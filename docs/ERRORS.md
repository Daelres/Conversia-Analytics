# Unexpected errors: the error registry

Every **unexpected** error of the API is recorded in the database under a unique, human-friendly
code. The client receives the code, so a user can quote it in a ticket and support finds the full
context with one query. Known outcomes (validation, `401`, `403`, `404`, `409`, `429`, ...) are
not errors in this sense and are never registered.

The API side comes first; [the Web side](#the-web-side) shows the code and reports the Web's own errors.

## What is registered, and what is not

Registered: the exceptions that reach the generic `catch` of `ExceptionHandlingMiddleware` (and
the errors the Web reports through [the report endpoint](#the-report-endpoint)).

Never registered, never answered with a code:

| Case | Answer | Why |
|---|---|---|
| Known application exceptions (duplicate e-mail/SKU, not found, stale `rowVersion`, invalid credentials, domain rules) | their own `4xx` | They are the system working as designed. |
| Validation and model-binding problems, unknown routes, `401`, `403`, `429` | their own `4xx` | Same. |
| The client went away (`OperationCanceledException` while `RequestAborted` is cancelled) | no body, status `499` | Nobody to answer, nothing broken. |
| `BadHttpRequestException` (malformed, too slow, too big request) | its own `400`/`408`/`413` as Spanish `problem+json` | The caller's doing, not a defect. |

An `OperationCanceledException` that is *not* the client leaving **is** an unexpected error.

## The code

`ERR-yyyyMMdd-XXXXXX`: the UTC date, then six characters of the Crockford base32 alphabet
`0-9 A-H J K M N P-T V-Z` (uppercase; never `I`, `L`, `O`, `U`, so a code survives being read
aloud or typed). Generated by `ErrorCode.New` (Domain) from `RandomNumberGenerator`, 5 bits per
character (32 symbols, so no modulo bias); `ErrorCode.IsValid` accepts exactly that format. There are
32^6 (about 1.07 billion) codes per day, and the unique index on `ErrorLogs.Code` arbitrates the
rare collision: the insert is retried with a new code (up to 5 attempts).

## What the client receives

An unexpected error answers `500 application/problem+json` with the **unchanged** Spanish `title`
and `detail` (no exception text, no stack trace), plus the code:

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json
X-Error-Id: ERR-20261018-7K3M9Q

{ "title": "Ocurrió un error inesperado", "status": 500,
  "detail": "Ocurrió un error inesperado. Inténtalo de nuevo más tarde.",
  "errorId": "ERR-20261018-7K3M9Q" }
```

`errorId` (body) and `X-Error-Id` (header) always carry the same code. If the response had already
started when the failure happened, nothing can be appended: the error is still registered and
logged, and the connection is aborted.

The code is also written to the log as the structured property `ErrorId` of the `Error` entry that
carries the exception, so the log and the table join on it.

## What is stored (and what deliberately is not)

One row of `ErrorLogs` (an operations table: **no tenant filter**, it is meant to be read by
support across tenants; it stores `TenantId` and `UserId` as data).

| Column | Content |
|---|---|
| `Code` | `ERR-yyyyMMdd-XXXXXX`, unique (`varchar(24)`) |
| `OccurredAt` | UTC (`timestamptz`) |
| `Source` | `1` Api, `2` Web (int) |
| `Kind` | `1` Unhandled, `2` UpstreamUnavailable, `3` UpstreamBadResponse (int) |
| `Environment`, `ServiceVersion`, `Instance` | `IHostEnvironment` name; `AssemblyInformationalVersion` without the `+sha` build metadata; machine name |
| `HttpMethod`, `Path` | method and path, **without** the query string |
| `Query` | the query string, sensitive values redacted |
| `Endpoint` | the endpoint display name, e.g. `Conversia.API.Controllers.ProductsController.UpdateProduct (Conversia.API)` |
| `RouteValues` | JSON of the route values |
| `StatusCode` | `500` for the API |
| `TraceId` | W3C trace id (`Activity.Current`) |
| `RequestId` | `HttpContext.TraceIdentifier` |
| `UserId`, `TenantId` | the `sub` and `tenant_id` claims of an authenticated caller |
| `UserAgent` | the `User-Agent` header |
| `ExceptionType`, `ExceptionMessage` | full type name and message |
| `ExceptionDetails` | `exception.ToString()`, inner exceptions included, sanitized, at most 16 000 characters (`text`) |
| `Fingerprint` | `character(16)`, see below |
| `Context` | free JSON given by the reporter (the Web) |
| `Id`, `CreatedAt`, ... | `BaseEntity` audit columns |

Indexes: unique on `Code`; on `OccurredAt` (retention, "latest"); on `(Fingerprint, OccurredAt)`
(grouping).

**Never stored:** request or response bodies, headers (so no `Authorization`, no `Cookie`), cookies,
tokens, passwords, the client IP address, and the values of sensitive query parameters.

## Sanitization

Applied on the server to **every** report, whatever its source (the Web's payload is not trusted
either), by `ErrorSanitizer` (pure, idempotent):

- **Secrets become `***`**: the value after `password`, `pwd`, `passwd`, `secret`, `apikey`,
  `api-key`, `api_key`, `token`, `access_token`, `refresh_token`, `authorization`, `signingkey`,
  `client_secret`, `connectionstring`, `accesskey` / `access-key`, `privatekey` / `private-key`,
  `subscriptionkey` / `subscription-key` (so `Ocp-Apim-Subscription-Key: abc` too) or `User Id`
  (connection strings), followed by `=` or `:` (JSON style `"password":"x"` too, any case).
  - A value that opens with a quote (`"`, `'`, or the escaped `\"` of JSON inside JSON, at any
    depth: `\"`, `\\"`, `\\\"`...) runs to its closing quote, so spaces, `;` and the other quote
    kind inside it are redacted too (`Password="my secret pass";x` becomes `Password="***";x`).
  - Inside a quoted value, a **doubled quote is an escaped quote, not the end** (SQL / connection
    string style): `Password='it''s a secret';x` becomes `Password='***';x` and
    `Password="say ""hi"" there";x` becomes `Password="***";x`. Inside double quotes a `\x`
    escape does not close the value either. An unterminated quote redacts the rest of the text.
  - An **unquoted** value runs up to whitespace or `;`, backslashes and quotes included
    (`pwd=abc\def;` becomes `pwd=***;`, `Password=p@ss'word` becomes `Password=***`, and
    `password=a,b` becomes `password=***`), with these stops so it does not eat the data around
    it: a quote that is followed by `,`, `}`, `]`, whitespace, `;` or the end of the text ends the
    value (`{"msg":"password=abc","user":"ana"}` keeps its closing quote and `"user":"ana"`); and
    when the key itself is quoted (`"password":null`, JSON or dictionary style) the value also
    stops at `,`, `}` and `]` (`{"token":123,"user":"ana"}` becomes `{"token":***,"user":"ana"}`).
- **`Bearer <token>`** becomes `Bearer ***`; **JWT-shaped** strings become `[jwt]`.
- **Query strings**: keys and benign values are kept; the value of a sensitive key is `***`. The key
  is URL-decoded and normalised (lowercase, without `_`, `-`, `.` and spaces) and is sensitive if it
  **contains** `password`, `passwd`, `pwd`, `secret`, `token`, `apikey`, `authorization`,
  `signingkey`, `connectionstring`, `signature`, `accesskey`, `privatekey` or `subscriptionkey`, or
  if it is exactly `key`, `sig` or `User Id`. So `newPassword`, `accessToken`, `clientSecret`,
  `id_token`, `X-Api-Key` and `X-Amz-Signature` are redacted, while `page`, `sort`, `id`, `code`,
  `keyword`, `monkey` and `sigma` are kept (`key` and `sig` match only as the whole key, because
  they are too common inside other words; a few ordinary words that contain a sensitive word,
  such as `tokenizer`, `passwordless` and `secretary`, are not treated as sensitive). The free-text
  rule above uses the same words, right before the `=` or `:`; only `signature`, `sig` and `key`
  are query-only (in free text `keyword=abc` or `the key: x` is ordinary text and stays).
- **Control characters** are removed, except `\n`, `\r` and `\t` (a stack trace stays readable).
- **Truncation** to the column length ends with the visible marker `…[truncado]`; a secret is
  redacted *before* the cut, so a cut can never leave half of one visible.
- Benign text is returned unchanged. Matching uses the non-backtracking regex engine under a
  2-second timeout, so hostile input costs linear time. If a pattern ever does time out, the
  **whole text** of that field becomes `***` (fail closed). The fingerprint is computed from
  the *sanitized* `ExceptionType` and `ExceptionDetails`, so if either one timed out the top frame
  or type is lost and unrelated defects can end up with the same fingerprint. It needs input crafted
  to hit the timeout, which the non-backtracking engine makes very unlikely.

Redaction is about secrets, **not about markup**: see the [stored-XSS caveat](#stored-xss-caveat).

## Fingerprint

`Fingerprint` groups the repeated occurrences of one defect: the first 16 lowercase hex characters
of SHA-256 over `ExceptionType + "|" + topApplicationFrame`. The top application frame is the first
`Conversia.` frame of the stack as `Namespace.Type.Method` (the first frame if there is none).
Messages, line numbers, file paths, arguments, offsets, generic arity and compiler-generated names
(`<Run>d__3.MoveNext`, lambdas) are left out, so a redeploy or another message does not split one
defect into several.

## Storm control

An error that repeats thousands of times must not flood the table or the database. A sliding
window per fingerprint lets `ErrorLogging:MaxPerFingerprintPerMinute` (default 20) occurrences per
minute through (in memory, thread-safe, per process). A refused occurrence still gets **a code
(which is returned) and an `Error` log entry with the key fields** (code, source, fingerprint, path,
exception type and message), reports `persisted = false` and costs no database command. Only
occurrences that are let through count toward the window, so refusals do not extend the block.

## How it is persisted

- With a **fresh `IServiceScope` and `DbContext`** — never the request's: that context may be exactly
  what failed (a rejected write, a disposed connection).
- Awaited before the response is written, bounded by `ErrorLogging:PersistTimeoutSeconds`
  (default 3).
- **One `INSERT` per error**; no read on the error path (a unique-index violation is the only reason
  to retry, with a new code).
- **Never throws and never masks the original error.** If the insert fails (database down, slow,
  collisions exhausted) the registry logs an `Error` entry with the code and the key fields and
  answers `persisted = false`; the request still ends in the normal `500` with the code.
- `ErrorLogging:Enabled=false`: the code is generated, returned and logged; nothing is stored and
  the retention service does not run.

## Configuration

Validated at startup like the other settings (an invalid value stops the API with an
`InvalidOperationException` naming the key; the report key is never printed). A blank value means
"use the default".

| Key | Default | Description |
|---|---|---|
| `ErrorLogging:Enabled` | `true` | `false`: codes are generated, returned and logged, nothing is stored. |
| `ErrorLogging:RetentionDays` | `90` | Rows older than this are purged. `1` to `3650`. |
| `ErrorLogging:MaxPerFingerprintPerMinute` | `20` | Storm control budget per fingerprint and minute. `>= 1`. |
| `ErrorLogging:PersistTimeoutSeconds` | `3` | How long a request waits for the insert. `1` to `30`. |
| `ErrorLogging:ReportRateLimitPerMinute` | `60` | Report endpoint budget per client IP and minute. `>= 1`. |
| `ErrorLogging:ReportKey` | *(unset)* | Shared secret of the report endpoint, at least 32 characters. **Unset: the endpoint is off.** Set it with user secrets or an environment variable (`ErrorLogging__ReportKey`), never in a committed file. |

## The report endpoint

`POST /api/diagnostics/errors` is how the Web, which has no database, reports its own errors.

- **Off unless `ErrorLogging:ReportKey` is configured**: otherwise the route answers `404`.
- **Not JWT-authenticated.** The caller sends the key in the header `X-Error-Report-Key`
  (nowhere else). It is compared in constant time (`CryptographicOperations.FixedTimeEquals` over
  SHA-256 hashes of fixed length). Missing or wrong: `401` without detail, nothing stored.
- **Rate limited** by its own policy (`ErrorLogging:ReportRateLimitPerMinute` per IP), applied
  *before* the key is checked so that guessing the key is throttled too: `429` with `Retry-After`.
- **Size**: the body is capped at **64 KB** (`413`): by `Content-Length` up front and by counting
  the bytes while reading.
- The stored `Source` is **always Web**, whatever the payload says. The API computes the fingerprint
  and chooses the row's identity; the payload cannot.

Request body (JSON; unknown members are ignored):

| Field | Required | Limit | Notes |
|---|---|---|---|
| `kind` | yes | | `Unhandled`, `UpstreamUnavailable` or `UpstreamBadResponse` |
| `path` | yes | 500 | |
| `exceptionType` | yes | 300 | |
| `code` | | | A code the Web already showed to its user; honored only if valid and unused, else replaced |
| `httpMethod` | | 10 | |
| `query` | | 1000 | sanitized |
| `endpoint` | | 300 | |
| `routeValues` | | 1000 | |
| `statusCode` | | | integer |
| `traceId` / `requestId` | | 64 / 100 | |
| `userId` / `tenantId` | | | GUIDs |
| `userAgent` | | 300 | |
| `exceptionMessage` | | 2000 | |
| `exceptionDetails` | | cut at 16 000 | the full `exception.ToString()` |
| `context` | | 2000 | |
| `environment` / `serviceVersion` / `instance` | | 50 / 50 / 100 | |
| `occurredAt` | | | ISO 8601; a date more than a day old or more than 5 minutes in the future is replaced by the server's clock (up to 5 minutes ahead is tolerated, for clock skew) |

| Status | Meaning |
|---|---|
| `201` `{ "code": "ERR-...", "persisted": true }` | Registered. `persisted` is `false` when storm control, `Enabled=false` or a database failure kept it from being stored; the code is valid and logged all the same. |
| `400` | A required field missing or blank, a field over its limit, an unknown `kind`, a value of the wrong type (non-GUID ids...), a body that is not JSON: Spanish `problem+json` with the field name. |
| `401` | Missing or wrong key. No detail. |
| `404` | No `ReportKey` is configured (also: other methods on the route answer `404`/`405`). |
| `413` | Body over 64 KB. |
| `429` | Over the rate limit; `Retry-After` in seconds. |
| `500` | A failure inside the endpoint: the normal generic `500` with its own code. It never reports itself in a loop. |

## Retention

`ErrorLogRetentionService` (a `BackgroundService`) purges at startup **without delaying the host**
(it runs beside it) and then every 24 hours. `IErrorLogPurger.PurgeAsync(olderThanUtc)` deletes in
batches of 1 000 rows (`DELETE ... WHERE "Id" IN (SELECT ... ORDER BY "OccurredAt" LIMIT 1000)`, one
statement per batch, served by the `OccurredAt` index) and returns the count. A failed run is logged
and tried again at the next one; it never stops the host.

## Ready-to-use SQL

PostgreSQL folds unquoted identifiers to lower case, so table and column names are quoted.

```sql
-- One error by the code the user quoted
SELECT * FROM "ErrorLogs" WHERE "Code" = 'ERR-20261018-7K3M9Q';

-- The latest 50 errors (without the long text)
SELECT "OccurredAt", "Code", "Source", "Kind", "StatusCode", "HttpMethod" AS "Method", "Path", "ExceptionType", "ExceptionMessage"
FROM "ErrorLogs" ORDER BY "OccurredAt" DESC LIMIT 50;

-- Defects ranked by how often they happen, with first and last occurrence
SELECT "Fingerprint", COUNT(*) AS "Occurrences", MIN("OccurredAt") AS "FirstSeen", MAX("OccurredAt") AS "LastSeen",
       MAX("ExceptionType") AS "ExceptionType", MAX("Endpoint") AS "Endpoint"
FROM "ErrorLogs"
WHERE "OccurredAt" >= now() - interval '7 days'
GROUP BY "Fingerprint" ORDER BY "Occurrences" DESC;

-- Every occurrence of one defect
SELECT "OccurredAt", "Code", "TenantId", "UserId", "Path", "ExceptionMessage" FROM "ErrorLogs"
WHERE "Fingerprint" = '0123456789abcdef' ORDER BY "OccurredAt" DESC;

-- Everything one request left behind (the trace id also appears in the application log)
SELECT * FROM "ErrorLogs" WHERE "TraceId" = '4bf92f3577b34da6a3ce929d0e0e4736' ORDER BY "OccurredAt";

-- What a tenant or a user ran into
SELECT "OccurredAt", "Code", "Source", "Path", "ExceptionType" FROM "ErrorLogs"
WHERE "TenantId" = '00000000-0000-0000-0000-000000000000' ORDER BY "OccurredAt" DESC;
SELECT "OccurredAt", "Code", "Source", "Path", "ExceptionType" FROM "ErrorLogs"
WHERE "UserId" = '00000000-0000-0000-0000-000000000000' ORDER BY "OccurredAt" DESC;
```

## Stored-XSS caveat

The sanitizer removes **secrets**, not markup. Every stored text (`ExceptionMessage`, `UserAgent`,
`Path`, `Context`, ...) is influenced by whoever caused or reported the error, so it may hold
`<script>...</script>` or other markup, stored verbatim. **Any UI, report or export that displays
these values must HTML-encode them** (Razor does by default; raw HTML, `MarkupString`, `innerHTML`,
spreadsheet formulas in CSV exports do not).

## Limits

- **Best effort.** Persistence is bounded by `PersistTimeoutSeconds` and is allowed to fail; the
  request still answers with its code.
- **Storm suppression** is deliberate: past the budget, occurrences of one fingerprint get a code and
  a log entry but no row. The window is per process (several instances each have their own budget).
- **No persistence when the database itself is down.** The code is still returned to the client and
  logged with all the key fields (code, source, fingerprint, path, exception type and message), so
  the log is the fallback record.
- **Redaction limits.** A quoted secret is redacted up to its matching closing quote; an unquoted
  one stops at whitespace or `;`, so a secret with spaces that is *not* quoted keeps the words
  after the first space (`password=my secret` becomes `password=*** secret`). An unquoted value
  can still swallow quotes and backslashes up to the next whitespace or `;` (for example
  `password=ab\cd` is redacted whole), but it stops at a quote followed by `,`, `}`, `]`,
  whitespace or `;`, and, after a quoted key, at `,`, `}` and `]`. The flip side: an unquoted
  secret that itself contains such a quote (`pwd=ab",cd`) or, after a quoted key, a comma, brace or
  bracket, is cut there and the rest is stored. A JSON-escaped value (`\"x\"`) closes at the first
  run of backslashes plus a quote, whatever its depth, so a secret that itself contains an escaped
  quote of another depth may keep its tail. Query keys are judged by
  the words listed under [Sanitization](#sanitization); a secret under a key that contains none of
  them (and is not `key` or `sig`) is stored.
- **Behind a reverse proxy** the per-IP rate limits (the login policy and the report endpoint's
  `ErrorLogging:ReportRateLimitPerMinute`) see the **proxy's IP** unless the API is configured with
  forwarded headers (`UseForwardedHeaders` with `KnownProxies` or `KnownNetworks`, i.e. trusted
  proxies only: never trust `X-Forwarded-For` from anyone). Without that, every client shares one
  budget, and the Web's error reports compete with anonymous traffic for the same budget (and a
  burst of failures can be throttled with `429`). Configure the forwarded headers whenever the API is
  deployed behind a proxy or load balancer.
- The registry stores what the sanitizer's rules can recognise as a secret. A secret in a shape no
  rule knows is stored; do not put secrets in exception messages.
- The first error after a process starts may be slower (the data model is built lazily); the startup
  purge warms it up.

## The Web side

The Web has no database, so it shows the same kind of code for **its own** unexpected errors and for the API's, and registers its
own through [the report endpoint](#the-report-endpoint). The code is in the shared layouts and components: no page shows or
mentions it.

### What is reported, and what is not

| Case | Code shown | Reported by the Web |
|---|---|---|
| An exception nobody handled in the Web (a page, an enhanced navigation, a form post) | on the `500` error page and in `X-Error-Id` | yes, kind `Unhandled` |
| The API answered `500` with `errorId` / `X-Error-Id` | the API's code | **no**, the API already registered it (only `500` is trusted, and only a well-formed code) |
| The API is unreachable, timed out, or answered `502`/`503`/`504` | a code of the Web | yes, `UpstreamUnavailable` |
| The API answered something unusable (a `500` without a code, HTML, truncated JSON, an unexpected status) | a code of the Web | yes, `UpstreamBadResponse` |
| Known outcomes (validation, `401`, `403`, `404`, `409`, `429`) | none | no |
| The browser abandoned the request | none | no |

### How the code flows

1. `ApiClient` turns every "service unavailable" outcome into an `ApiResult` with an `ErrorCode`: the API's own, or the one the
   Web reporter returned (a local code if there is no reporter, or it failed: the person always has one).
2. The code is recorded in the per-request `ErrorCodeState`. `ErrorCodeNotice`, rendered by `MainLayout` and `AuthLayout`, shows
   `Código de error: ERR-...` in an `role="alert"` element (`data-testid="error-code"`). With several failed calls one code is shown.
   A failed grant/revoke carries its code across the redirect to `/users` (`?notice=unavailable&errorId=...`).
3. An unhandled exception reaches `WebExceptionHandler`, which reports it, puts the code in `X-Error-Id` and hands it to the
   `/Error` page that the exception-handler middleware renders (`500`, Spanish, no internals). A response that had already
   started cannot carry a code: the middleware logs it and aborts, as for the API.
4. Every report is logged as an `Error` entry with the code (`ErrorId`) and the original exception, whatever happened to the
   report, so the log is the fallback record.

### What is sent

`POST {Api:BaseUrl}api/diagnostics/errors` with the header `X-Error-Report-Key` and the [report body](#the-report-endpoint):
the failed request's method, path, query, endpoint and route values, the signed-in user and workspace (claims of the auth
cookie), trace id, request id, user agent, the exception type, message and `ToString()`, the environment, version and machine name,
and for a failed API call its method and path (without query) in `context`. Everything is sanitized with the Application's
`ErrorReportSanitizer` before it leaves the Web. **Never sent:** cookies, the `Authorization` header or any token, request bodies
and forms (so no typed e-mail or password), other headers, and the key (only in its header, never in a log or a page).

### Configuration

Validated at startup (an invalid value stops the Web with an `InvalidOperationException` naming the key; the key is never
printed). A blank value means "use the default".

| Key | Default | Description |
|---|---|---|
| `ErrorReporting:Enabled` | `true` | `false`: codes are still shown and logged, nothing is sent. |
| `ErrorReporting:ApiKey` | *(unset)* | The API's `ErrorLogging:ReportKey`, at least 32 characters. **Unset: nothing is sent**, the Web only logs its codes. Never put it in a committed file. |
| `ErrorReporting:TimeoutSeconds` | `2` | Wait for the API's answer, `1` to `30`. One attempt, no retries; the request is cancelled when it expires. |
| `ErrorReporting:MaxPerFingerprintPerMinute` | `20` | Storm control per defect (the same fingerprint as the API's), in memory per process. `>= 1`. |

### ERROR_REPORT_KEY

One shared secret for both sides. `docker-compose.yml` passes `ERROR_REPORT_KEY` to the API as `ErrorLogging__ReportKey` and to the
Web as `ErrorReporting__ApiKey` (the demo overlay inherits it); it is empty by default, which leaves the endpoint off and the
Web logging only. Set it in `.env` (at least 32 characters, `openssl rand -base64 48`), or as a user secret / environment
variable. The Web sends it only in the `X-Error-Report-Key` header; the API answers `401` to a wrong one and `404` when it has none.

### Limits

- **Best effort.** One attempt per report, bounded by `ErrorReporting:TimeoutSeconds`; a failed report (API down, `401`, `404`,
  `429`, a slow or garbled answer) never changes what the person sees and is not retried. While the API is down, the error
  page waits at most that timeout.
- **Storm control is per Web process** and per defect: past the budget an occurrence still gets a code and a log entry but is not
  sent, so an outage of the API costs at most `MaxPerFingerprintPerMinute` attempts a minute, not one per request. An API outage is
  one defect (same exception type and top frame), so all its failures share the budget.
- **The API's answer decides the code:** if it stored the report under another code (a collision), that one is shown.
- **Not reported:** failures after the response started (logged by the middleware), and Development, where the developer
  exception page replaces the error page. To see the code for an unhandled exception, run with `ASPNETCORE_ENVIRONMENT=Production`
  (or `Demo`); the code of an API failure ("service unavailable") is shown in every environment.
- The report endpoint's own limits apply: 64 KB, a rate limit per IP shared with anonymous traffic behind a proxy, sanitization limits.
